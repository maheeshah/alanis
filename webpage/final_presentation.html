Name Location Service · Final Presentation

ALANIS

From raw rail messages to a live location map
A data pipeline and mapping tool that turns encoded railroad messages into named, mapped, GPS-accurate track locations and shows trains running in real time.
SLIDE·00 The problem

Locations live in code, not on a map

Railroad operations generate a constant stream of encoded messages — track warrants, bulletins, position updates. Buried inside them are the locations that matter: where a train can go, where it stops, where the limits of authority are.

But those locations arrive as subdivision IDs, track names, and mileposts , not coordinates. There was no single place to search a location by name, see it on a map, or line it up against the trains actually running.

SLIDE·01 Why it matters · Trip Optimizer Zero to Zero

Stopping a train, by name

With Trip Optimizer Zero to Zero, a train can run start-to-stop on its own but today there's no simple way to tell it where to stop. Someone has to hand-enter the track details and push them to the train.

Alanis fixes that: pick the stop by its name, and the exact location is sent straight to the train.

CREW → DISPATCHER

"We won't make the crew-change point on our hours of service. Set a stop at Hoover and send a crew van."

RESULT

The stop goes straight to the on-board system and the train comes to a stop automatically, with no manual track entry.

SLIDE·02 The bigger picture · RODA

A building block for RODA

Stopping a train is the first use but the real vision is bigger. RODA, the Railroad Operations Digital Assistant, is an application that allows any user to query it to answer questions.

Alanis is the piece that identifies track locations for any purpose - the foundation RODA would be built on.

ASK RODA…

"What's at milepost 157.9 on the Davenport Sub?"
"Show me every siding on this subdivision."

Alanis resolves the locations behind every answer.

SLIDE·04 First we had to read the messages
From bytes to fields

Decoding the messages

  • The logs live in S3 buckets which is cloud storage holding millions of files; we then filtered to about two weeks of files to keep the data load manageable
  • BNSF stored theirs differently from everyone else, so it needed its own path
  • We decoded only 1041 (bulletins) and 1051 (authorities) — the messages that name track locations
  • Turned the raw hex into clean fields, reassembling messages split across many lines
Now every message is readable but it still has no coordinates.

SLIDE·05 The other half of the picture
The map of the ground

What track files give us

A track file is the railroad's fixed map of the physical network, assembled from over 1,000 customer track databases.

For every point on the track it lists a real GPS coordinate — exactly the thing our decoded messages are missing.

The messages know the place. The track files know where it is.

SLIDE·07 Bridge the two together
Message ⋈ track file

Matching them up

We take the subdivision, prefix/suffix, track and milepost from the decoded message and look up the same point in the track files.

Out comes the exact lat/lon. That's the bridge and it's what finally lands each location on the map.

SLIDE·09 The application

Meet Alanis

A web app built with Leaflet that brings the whole pipeline together on one map — pulling four sources at once.

SLIDE·10 What it does — and why it matters

Search by name

Find a location the way crews say it — by name — and jump straight to it. No coordinates required.

See a train's route

Enter a train ID and highlight the route it runs — the context you need to place a stop correctly.

Live running trains

Pull current trains from DART and watch them move — refreshed every 30 seconds, in place.

Toggle track detail

Show or hide signals, switches, crossings and mileposts — straight from the track files.

Set a stop

Pick where a train ends — and it's validated against that train's own route so a bad stop is caught.

Snaps to the rail

Click near the track and it snaps to the line, then interpolates the exact milepost — accurate, not fiddly.

SLIDE·11 The hard parts · data & decoding

Challenges — getting the data right

APPENDING HEX PAYLOADS

A single message came in as hex spread across many log lines. I had to append the pieces in the right order before anything could be decoded. The ICD is incredibly strict so even if the message was off by just a byte, the whole message was garbage.

KEEPING MEMORY IN CHECK

Millions of records wouldn't fit in memory at once. I had to stream the files in batches and released as we went, so it stayed within limits instead of crashing.

EDGE CASES

Some messages didn't follow the spec — missing fields, odd lengths, BNSF used a different ICD version. Each one had to be detected and handled rather than allowed to break the parser.

SLIDE·12 The hard parts · building the app

Challenges — making it usable

BUILDING A DART PROXY

A browser can't call DART directly — keys and cross-origin rules block it. I built a small local proxy to forward the request and keep the key server-side. First time building one, so a real learning curve.

INTERPOLATION

Turning a map click into an exact milepost meant projecting onto the rail line and interpolating between known mileposts. Getting it to land accurately took real iteration.

A FUNCTIONAL WEBPAGE

Wiring live data, layer toggles, search and validation into one responsive map that stays usable and doesn't jump around every time the live data refreshes.
